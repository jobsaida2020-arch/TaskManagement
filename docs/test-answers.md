## Q2. IPアドレスとポート番号

このプロジェクトではフロントエンドを `localhost:5173`、バックエンドを `localhost:8080` で起動しています。

- `localhost`とは何を指しますか？
- `:5173` や `:8080` のようなポート番号はなぜ必要ですか？

**回答:**
`localhost`とは何を指しますか？
→自身が使用しているマシン（パソコン、スマホなどの機器）を指します。

`:5173` や `:8080` のようなポート番号はなぜ必要ですか？
→とあるデータを特定のプログラムに送る為に必要です。
基本的な仕組みとしてデータのやり取りはIPアドレスとポート番号を用いて行います。1つのマシン上で複数のプログラムが動いており、IPアドレスでマシンの特定、ポード番号で特定したマシン内のプロクラムの特定を行なっています。

## Q5. HTTPとHTTPSの違い

HTTPとHTTPSの違いは何ですか？

なぜ現在のWebサイトはほぼすべてHTTPSを使用していますか？

**回答:**
違いは主に2つあります。
1つは通信が暗号化されているか否か。暗号化されているのがHTTPSです。
もう1つはポート番号がHTTPが80番、HTTPSが443番を使用します。

Webサイトのセキュリティ、信頼性、検索順位、パフォーマンスなど多くの観点でHTTPよりもHTTPSが有利になったことでHTTPS使用がデフォルトになっています。

## Q8. HTTPステータスコード

## Q10. APIとは

このアプリではフロントエンドがバックエンドのAPIを呼び出してデータを取得しています。

- APIとは何ですか？
- なぜ直接データベースにアクセスしないのですか？

**回答:**
APIとはインターフェース（＝窓口）の事です。

直接データベースにアクセスしない理由は3つ。
1、セキュリティ面
フロントエンドはブラウザ上で動く為、DBへ直接アクセスするとその情報が容易に取得されてしまい危険な為。
2、ルールの遵守
ルールを決めていたとしてもDBへのアクセスがAPI経由以外で可能であればルールを守らせる仕組みを機能させることができない為。
3、データベースの変更が容易
データベース構造を変更した時、直接データベースへアクセスする設計であればフロントエンド側のコード変更も必要となり大変になる為。

## Q14. 3層構造

このアプリは

- フロントエンド
- バックエンド
- データベース

の3層構造です。

なぜこのように役割を分けるのですか？

1つのプログラムですべてをやらない理由を説明してください。

**回答:**
そもそも役割が違うものを1つの同じ括りの中で動かすことがナンセンスです。
フロントエンドは見た目・操作性が、バックエンドは複雑な計算・ルールを扱うことが、データベースはデータそのものを扱うことが求められます。1つの技術で全てを網羅しようとすると中途半端になります。
また異なる役割を1つにまとめることで、小さな修正による影響範囲が読めなくなったり、セキュリティが確保されなかったり、技術の再利用ができなかったりと多方面で使い勝手が悪くなってしまうことも理由です。

## Q17. 同期処理と非同期処理

「同期処理」と「非同期処理」の違いを、日常生活の例えで説明してください。

なぜWeb通信では非同期処理が必要ですか？

**回答:**
家事に例えると、全自動洗濯機で洗濯を開始してから完了するまで見張っているのが「同期処理」、洗濯を開始したら完了するまで他の家事を行い、完了を通知で知るのが「非同期処理」です。

非同期処理が必要な理由は3つ。
1、同期処理だと進行中処理完了まで他の一切の操作ができなくなってしまう為
2、1によってユーザーの印象が悪化する為（パソコンがフリーズしたように見える）
3、処理待ちの時間に、他の処理が進められず全体の効率が下がる為

## Q19. 入力チェック（バリデーション）の多重防御

入力チェックはフロントエンドとバックエンドの両方で行うべきと言われています。

なぜ片方だけでは不十分なのですか？

**回答:**
フロントエンド側のチェックはUX目的（悪意をもった攻撃に対する防御はできない）であり、バックエンド側のチェックはセキュリティ・データ整合目的（入力エラー1つもサーバーからのレスポンスがあるまで気付けないなどUXが悪い）である。それぞれチェック目的が異なっており、片方で他方の役割を担うことができない為、両方で行うべきと言われています。

## Q20. エラーハンドリング

API呼び出しが失敗した場合（ネットワーク障害やサーバーエラーなど）、

アプリはどのように対処すべきですか？

**回答:**
4つの対処が必要と考えます。
1、エラー原因が不明な状態で処理を止めないこと。
2、ボタンを無効化するなどし、データの二重送信やユーザーの誤操作を防ぐこと。
3、エラーをUI上にメッセージ表示させ、ユーザーに把握させること。
4、楽観的更新を行う場合、失敗時は変更前の状態に戻し、データの不整合を防ぐこと。

## Q25. データの制約

## Q27. トランザクション

トランザクションとは何ですか？

タスクを別カラムへドラッグ移動する操作で、なぜ重要ですか？

**回答:**
複数のDB操作を一つの「まとまり」として扱う仕組みがトランザクションです。「まとまり」内の処理が全て成功することで確定され、1つでも失敗すれば処理が取り消しされます。これにより一部だけ処理が成功し中途半端なデータがDBに残ることを防止します。

カラムまたぎ移動において①移動先カラム全タスクのposition再計算、②元カラムタスクのposition再計算の2つのデータ保存が発生します。トランザクションがない状態で仮に①が成功し②が失敗したとすると、元カラムではデータの重複もしくは欠番という矛盾を防止することができます。

# 第4章 開発プロセスとチーム開発（4問）

## Q29. バージョン管理（Git）

Gitなどのバージョン管理システムとは何ですか？

なぜ必要ですか？

使わないとどんな問題が起きますか？

**回答:**
ファイルの更新履歴を記録する仕組みのことです。チームで使うことができます。
メイン（ファイル本体）からブランチという独自の作業スペースを作成して作業し、完了後にマージ（統合）することができます。
講義の言葉を借りると、ゲームのセーブポイントのようなイメージになります。

チーム作業では複数人が同じプロジェクトコードを更新します。また、プロジェクトを進める上で多くの更新もかかります。この履歴を管理しておくことでエラー発生時にエラー発生前の状態に戻すことや履歴を辿ることでエラー箇所の特定に繋がる為必要です。

いつ誰が何をどのように追加・変更・更新・削除したかわからなくなります。またリリース後のサービスであれば本番環境を触ることになり、危険があります。（サービスが動かなくなるなど）

## Q30. ブランチとPull Request

- ブランチとは何ですか？
- Pull Request の目的は何ですか？
- なぜ全員が main に直接変更しないのですか？

**回答:**
ブランチとは作業を行う際に作成する自分専用の作業環境です。メインファイルの内容をコピーした内容になっています。

ブランチファイルをマージする前にプロジェクトメンバーにチェックしてもらうことがPull Request の目的です。

プロジェクトメンバーがmainを壊してしまうことを防ぎ、Pull Requestを用いてチェックする機会を増やすことができ、複数人が同時にmainを変更することで差分がわからなくなることを防げるのでmainに直接変更をしません。
