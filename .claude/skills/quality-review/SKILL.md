# 品質レビュー・チェックリスト

このプロジェクト(backend: Spring Boot / frontend: React)の実装をレビューする際に使う観点一覧。過去のレビューで実際に指摘が出た項目をベースにしている。

## 進め方

1. まず `docs/` 配下の要件定義書・機能要件書・画面設計書・データ設計書・技術スタックを読み、想定されている仕様・アーキテクチャ方針を把握する(学習用個人アプリのため過度な抽象化は求められていない、認証なしは意図的、等の前提を取り違えないため)。
2. backendとfrontendは調査観点が異なるため、範囲が広い場合はExplore系のサブエージェントに調査を並行して委譲してよい(それぞれ下記チェックリストを渡す)。
3. 指摘は「具体的なファイルパス・行番号」+「深刻度(高/中/低)」を添えて報告する。学習目的のシンプルさを損なう過剰な指摘(過度な抽象化の提案等)は避け、要件定義書に明記された前提(認証なし、localStorage→DB移行等の現状)と矛盾する指摘をしない。

## Backendチェックリスト(Spring Boot)

1. **レイヤー構成**: Controllerに業務ロジックが漏れていないか。ControllerがRepositoryを直接呼んでService層をバイパスしていないか。Serviceがエンティティをそのまま返していないか。
2. **例外処理**: グローバル例外ハンドラ(`@ControllerAdvice`/`@RestControllerAdvice`)の有無。適切なHTTPステータスコードを返しているか。
3. **DTOとEntityの分離**: EntityをそのままAPIレスポンス/リクエストに使っていないか。
4. **トランザクション管理**: 複数の更新処理(saveAll等)を含む複合操作に`@Transactional`が付与されているか。
5. **バリデーション**: Bean Validation(`@Valid`, `@NotBlank`等)が使われているか。Controller層での入力チェックの有無。
6. **N+1問題・非効率クエリ**: ソートをDB(`ORDER BY`)ではなくアプリ側で行っていないか、不要な全件取得がないか。
7. **セキュリティ**: CORS設定、SQLインジェクション対策(JPA/パラメータバインディング)、認証・認可があるべきなのに無い箇所(ただしこのプロジェクトは要件上ログイン機能なしが前提)。
8. **設定・秘密情報の扱い**: `application.properties`にハードコードされた秘密情報がないか(環境変数での上書き可否も確認)。
9. **命名規則・パッケージ構成**: Spring Bootの一般的な規約(package-by-feature/layerいずれかの一貫性)に沿っているか。
10. **テストの有無・カバレッジ**: `src/test`配下にテストが存在するか、Service/Controllerの主要ロジックをカバーしているか。

## Frontendチェックリスト(React)

1. **コンポーネント設計**: 責務が肥大化したコンポーネント(データ取得・モーダル状態・エラー処理を1つのコンポーネントに詰め込みすぎ等)、propsのバケツリレー、状態管理の妥当性。
2. **useEffectの誤用**: 不要なuseEffect、依存配列の不備、無限ループのリスク。
3. **状態管理**: ローカルstateとグローバルstateの使い分け、不要なグローバル化(このプロジェクト規模ではContext/Redux等は過剰な場合が多い)。
4. **APIコール**: fetch/axiosの直書き、エラーハンドリングの有無、ローディング状態の扱い。
5. **key props**: indexをkeyに使っていないか。
6. **TypeScriptの型の厳密さ**: `any`の多用、型定義の欠如。
7. **アクセシビリティ**: モーダルの`role="dialog"`/`aria-modal`/`aria-labelledby`、Escキー対応、カード等クリック要素のキーボード操作対応(`tabIndex`/`role="button"`/`onKeyDown`)。
8. **パフォーマンス**: 不要な再レンダリング、`useMemo`/`useCallback`の欠如や誤用(ただし過剰な最適化の指摘は避ける)。
9. **ディレクトリ構成**: `components/`, `api/`, `types/`, `hooks/`等、一般的なReactプロジェクトの慣習に沿っているか。

### Frontend lintチェック(必須)

`frontend/`ディレクトリで以下を実行し、エラー・警告を確認する:

```
npm run lint
```

(このプロジェクトはoxlintを使用。`react-hooks/exhaustive-deps`相当のチェックはESLintより弱いため、依存配列の不備は目視でも確認する。)

## 報告フォーマットの目安

- Backend/Frontendそれぞれ300〜500語程度で、指摘事項を深刻度順(高→低)にファイルパス・行番号付きで列挙する
- lint結果は指摘事項と分けて別途まとめる
- 最後に総括として、致命的な問題の有無と主な改善余地を1〜2文でまとめる
